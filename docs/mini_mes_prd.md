# Mini MES PRD 초안

- **프로젝트명:** Mini MES - 생산실적 및 LOT 추적 시스템
- **문서 상태:** 초안
- **작성일:** 2026-09-29
- **작성 근거:** 개발자가 제공한 프로젝트 목적, MVP 범위, 기술 스택, 개발 계획 4~21절
- **정책 표시:** 미확정 업무 규칙은 **설계 결정 필요(Business Decision Required)**로 표시한다.
- **해석 기준:** 이 문서는 요구사항 초안이며, 구현 또는 검증 완료를 의미하지 않는다. 권고 사항과 수용 기준은 개발자 검토 후 확정한다.

## 1. 프로젝트 목적

제조 업무 흐름을 중심으로 생산계획, 작업지시, 생산실적, 품질검사, LOT 추적이 연결되는 소규모 MES를 구현한다.

다음 역량을 실제 구현과 검증 기록으로 증명한다.

- Java/Spring 기반 업무 시스템 설계 및 개발
- 제조 업무 규칙과 상태 전이 설계
- DB 제약조건과 트랜잭션을 통한 데이터 정합성 유지
- AI 생성 코드의 검토, 오류 발견 및 수정
- Docker/Linux/Nginx 기반 배포와 데모 운영

성공 여부는 화면 개수보다 **생산 이력을 설명하고, 데이터 변경의 영향을 추적할 수 있는가**를 기준으로 판단한다.

## 2. 범위

### 2.1 MVP 포함

| 영역 | 기능 |
|---|---|
| 기준정보 | 품목, BOM 버전, 공정, Routing 관리 |
| 생산관리 | 생산계획, 작업지시, 생산실적 관리 |
| LOT 관리 | 원자재 LOT, 원자재 투입 이력, 완제품 LOT 관리 |
| 품질관리 | 불량 수량·내역, 품질검사 관리 |
| 추적관리 | 완제품 LOT 기준 원자재 역추적 |
| 운영 | Docker/Linux/Nginx 배포 및 데모 운영 |

**원자재 LOT 기준 완제품 정방향 추적**은 구현 목표로 두되, MVP 필수 여부는 설계 결정이 필요하다.

### 2.2 MVP 제외

- PLC 및 설비통신
- OPC UA, SECS/GEM 연동
- 공장 자동화 영역
- MSA 도입

### 2.3 범위 확정 필요

다음 기능은 현재 포함 여부가 확정되지 않았다.

- 원자재 예약
- 공정별 재공품 LOT
- LOT 분할·병합
- 창고·위치별 재고
- 구매·입고 업무 및 출하 업무
- 폐기 처리
- 로그인 및 역할별 권한

원자재 수량 관리에 필요한 최소 기능과 별도 재고관리 시스템의 범위는 구분하여 결정한다.

추가 확정 기준: 최종 품질검사의 재검사와 재작업은 MVP에서 제외한다. 폐기 처리 등 나머지 범위 확정 필요 항목은 그대로 유지한다.

## 3. 사용자

아래 구분은 **업무 역할 초안**이다. 실제 계정 권한과 역할 겸임 여부는 별도로 결정한다.

| 업무 역할 | 주요 업무 |
|---|---|
| 기준정보 담당자 | 품목, BOM, 공정, Routing 관리 |
| 생산관리 담당자 | 생산계획·작업지시 생성, 진행 현황 확인 |
| 생산 작업자 | 원자재 LOT 투입, 생산실적·불량 기록 |
| 품질 담당자 | 검사 결과 등록 및 검사 이력 확인 |
| 조회 담당자 | 생산 이력 및 LOT 추적 결과 확인 |

## 4. 주요 업무 흐름

1. 생산에 사용할 품목을 등록한다.
2. 제품별 BOM과 공정 순서인 Routing을 정의한다.
3. 생산계획을 등록하고 작업지시로 나눈다.
4. 작업지시에 적용할 BOM 버전과 Routing을 지정한다.
5. 원자재 LOT을 작업지시에 투입한다.
6. 생산수량, 양품수량, 불량수량을 기록한다.
7. 생산실적이 존재하고 0보다 큰 누적 생산수량이 지시수량과 같을 때 생산작업을 완료한다. 완료 시 확정된 누적 생산 양품에 최종 품질검사를 수행한다.
8. 완제품 LOT과 생산 이력을 연결한다.
9. 완제품 LOT에서 사용 원자재 LOT을 추적한다.

이번 MVP의 잠정 업무 규칙에서는 작업지시 생성 시 완제품 LOT을 만들지 않고, 최초 생산실적 등록 시 작업지시당 최대 하나의 완제품 LOT을 원자적으로 생성·연결한다. 이후 생산실적은 동일 LOT에 누적한다. 최종 품질검사는 작업지시 `COMPLETED` 이후에만 등록하며, 작업지시 생산 완료에 검사 완료·합격을 요구하지 않는다. 검사 대상 식별·중복 방지 구조와 부분 합격 LOT의 요약 상태 등은 후속 설계 항목으로 관리한다.

기존 요구사항에서 완제품 LOT 생성 시점에 대한 대안은 다음과 같이 정리한다.

| 대안 | 설명 | 고려사항 |
|---|---|---|
| 최초 생산실적 등록 시 LOT 생성 | 첫 생산실적에 LOT을 생성하고 이후 실적을 같은 LOT에 누적 | 이번 MVP 잠정 기준 |
| 검사 후 완제품 LOT 생성 | 생산실적 또는 별도 생산 LOT을 검사하고 이후 완제품 LOT 생성 | 이번 MVP 범위에서는 채택하지 않음 |

**적용 기준:** 품질검사 합격 여부와 완제품 LOT 생성은 별도 개념으로 관리한다. LOT별 누적 생산·생산 양품·생산 불량·검사 합격·검사 불합격·미검사 수량을 구분한다. 요약 품질 상태 및 가용수량 모델은 설계 결정 필요다.

## 5. 기능 요구사항

입력·출력 항목은 논리적인 데이터 목록이며, 필수 여부와 DB 컬럼은 후속 설계에서 확정한다.

### FR-01. 품목 관리

- **목적:** BOM, 생산계획, LOT에서 공통으로 사용할 품목을 식별한다.
- **주요 사용자:** 기준정보 담당자
- **입력 데이터:** 품목코드, 품목명, 품목구분, 관리단위, 사용 여부
- **처리 규칙:**
  - 같은 품목이 관련 업무에서 일관되게 참조되어야 한다.
  - 품목 변경이 기존 생산 이력을 훼손해서는 안 된다.
  - 품목코드는 ASCII, 최대 50자이며 전체 품목에서 유일하다. DB UNIQUE와 서버 검증을 함께 적용한다.
  - 품목구분은 RAW(원자재), SEMI(반제품), FINISHED(완제품)이다. MVP 신규 등록은 RAW·FINISHED만 허용하고 SEMI는 향후 확장용으로 유지한다.
  - 관리단위는 EA(개·정수), M(미터·소수 허용), G(그램·소수 허용)이다. 수량은 기존 DECIMAL(18,6) 설계를 따르며 단위 자동 환산은 하지 않는다.
  - 등록 후 품목코드·품목구분·관리단위는 변경하지 않는다. 품목명·사용 여부만 수정하며 서버에서도 불변 필드 변경을 거부한다.
  - 품목을 물리 삭제하지 않는다. 미사용 품목도 기존 이력·참조를 유지하고 신규 BOM 구성·신규 작업지시 대상에서 제외한다. 해당 신규 선택 제한은 각 업무 구현 시 적용한다.
  - 인증 도입 전에는 MES_ACTOR_ID 환경변수의 개발용 시스템 식별자를 created_by에 저장한다. 로컬 값은 LOCAL_DEV이며 인증된 사용자로 해석하지 않는다. 누락·공백 또는 컬럼 길이 초과 시 등록을 거부하고 화면에서는 작성자를 입력받지 않는다.
  - created_by는 등록 시에만 설정한다. 향후 인증 도입 시 분리한 ActorProvider에서 인증 사용자 ID를 제공하도록 변경하며 이번 범위에 로그인·권한 기능은 추가하지 않는다.
- **출력 데이터:** 품목 목록·상세, 사용 여부
- **예외 상황:** 코드 중복, 필수 데이터 누락, 등록 불가 구분·단위·사용 여부, 불변 필드 변경, 작성자 설정 누락, DB 저장 실패
- **연관 도메인:** BOM, Routing, 생산계획, 작업지시, LOT

### FR-02. BOM 관리

- **목적:** 제품 생산에 필요한 구성 품목과 소요량을 정의하고 버전별로 보존한다.
- **주요 사용자:** 기준정보 담당자
- **입력 데이터:** BOM 코드, 완제품, 양의 정수 버전 번호, 구성 원자재, 원자재별 기준 소요량. 기준 생산수량은 완제품 1 EA로 서버에서 설정한다.
- **처리 규칙:**
  - 작업지시 또는 생산 이력에서 당시 사용한 BOM 버전을 식별할 수 있어야 한다.
  - 최신 BOM 변경이 과거 생산 이력을 변경해서는 안 된다.
  - 2026-10-26 개발자 승인: 활성 FINISHED·EA 품목으로 신규 BOM/새 버전을 등록한다. 구성은 RAW 원자재 1개 이상이며 미사용 원자재의 신규 추가와 동일 버전 내 품목 중복을 금지한다.
  - 소요량은 양수, EA 정수, M·G 소수 6자리 및 DECIMAL(18,6) 범위로 검증한다. 자동 반올림·절삭·단위 환산을 하지 않는다.
  - BOM 코드는 전역 유일, 버전 번호는 BOM 헤더 내 유일하다. 등록한 BOM 코드·제품·버전 번호를 변경하지 않는다.
  - 사용 이력이 없는 버전은 소요량 수정과 구성 추가만 허용한다. 저장된 구성 제거·교체는 새 버전으로 작성하며 물리 삭제를 제공하지 않는다.
  - first_used_at 또는 작업지시 참조가 있는 버전은 수정하지 않는다. 현재 품목이 미사용이어도 기존 구성·이력은 조회·보존한다.
  - 별도 상태 컬럼이 없으므로 최초 사용 여부만 표시하며 수동 발행·활성 전이를 제공하지 않는다. 다단계 BOM·손실률·활성기간은 **설계 결정 필요**이며 이번 범위에서 제외한다.
  - 저장은 Service 트랜잭션으로 처리한다. 중복 등록은 기존 UNIQUE로, 구성 변경은 부모 잠금과 원본 비교값으로 보호한다. 작성자는 기존 ActorProvider/MES_ACTOR_ID를 사용한다.
- **출력 데이터:** 버전별 BOM과 구성 내역, 작업지시에 적용된 버전
- **예외 상황:** 유효하지 않은 소요량, 순환 구성, 사용 중인 버전 변경·삭제
- **연관 도메인:** 품목, 작업지시, 원자재 투입, LOT 추적

### FR-03. 공정 관리

- **목적:** Routing에서 사용할 생산 작업 단위를 정의한다.
- **주요 사용자:** 기준정보 담당자
- **입력 데이터:** 공정코드, 공정명, 설명, 사용 여부
- **처리 규칙:**
  - 여러 Routing에서 공정을 참조할 수 있어야 한다.
  - 공정 변경 후에도 기존 생산 이력을 해석할 수 있어야 한다.
  - 공정코드는 표시 가능한 ASCII 1~50자, 전역 유일이며 등록 후 변경하지 않는다. 명칭은 필수 200자, 설명은 선택 500자, 사용 여부는 0/1만 허용한다.
  - 명칭·설명·사용 여부만 수정하며 공정을 물리 삭제하지 않는다. 미사용 전환은 기존 Routing 참조·개정 사용 여부·process_name_snapshot을 변경하지 않는다. 미사용 공정의 신규 Routing 선택 차단은 후속 Routing Service에서 적용한다.
  - 작성자는 기존 MES_ACTOR_ID를 신규 등록에만 사용한다. 상세 확인은 수정 화면과 통합한다. 상세 정책은 BR-08을 따른다.
  - 공정별 실적·검사 등록 여부는 **설계 결정 필요**.
- **출력 데이터:** 공정 목록·상세
- **예외 상황:** 공정코드 중복, 사용 중인 공정의 비활성화·삭제
- **연관 도메인:** Routing, 작업지시, 생산실적, 품질검사

### FR-04. Routing 관리

- **목적:** 제품 생산에 필요한 공정과 수행 순서를 정의한다.
- **주요 사용자:** 기준정보 담당자
- **입력 데이터:** Routing 식별정보, 적용 품목, 공정 목록, 공정 순서
- **처리 규칙:**
  - 작업지시에서 적용한 Routing을 식별할 수 있어야 한다.
  - Routing 변경이 과거 작업지시의 공정 구성을 바꾸어서는 안 된다.
  - 현재 Routing 구현은 활성 FINISHED 제품의 헤더·개정·순번별 활성 공정을 등록한다(BR-09). 공정명은 서버가 저장 당시 스냅샷으로 보존하며 개정별로 조회한다.
  - 공정 구성 편집은 등록 전 폼에서 수행한다. 저장된 미사용 개정의 직접 수정은 미확정이므로 이번에는 덮어쓰기·삭제 없이 새 개정을 등록한다. 스키마에 없는 발행·활성 상태를 추가하지 않는다.
  - 기존 스키마의 개정 PK 참조와 공정명 스냅샷을 사용해 기준을 보존한다. 공정 생략·반복·병렬 실행과 저장된 미사용 개정 직접 수정 범위는 **설계 결정 필요**.
- **출력 데이터:** 품목별 공정 순서, 작업지시 적용 Routing
- **예외 상황:** 공정 누락, 순서 충돌, 사용할 수 없는 공정 참조
- **연관 도메인:** 품목, 공정, 작업지시, 생산실적

### FR-05. 생산계획 관리

- **목적:** 생산 대상과 목표수량·일정을 정의하고 작업지시 배분 현황을 관리한다.
- **주요 사용자:** 생산관리 담당자
- **입력 데이터:** 계획 식별정보, 생산 품목, 계획수량, 계획 일정
- **처리 규칙:**
  - 하나의 생산계획을 여러 작업지시로 나누는 흐름을 지원한다.
  - 계획수량과 작업지시 배분수량을 구분하여 조회한다.
  - 5차 구현은 기존 production_plan의 제품·양의 정수 수량·계획일 등록, 계획 ID/제품 검색 및 상세 조회를 제공한다(BR-10). 현행 스키마에 없는 계획코드·계획 상태는 추가하지 않는다.
  - 수량은 DECIMAL(18,6)과 전체 행의 정수 CHECK를 준수한다. 계획 수량 0은 이번 등록 요구에 따라 거절한다. BOM/Routing 지정과 작업지시 생성은 계획 단계에서 수행하지 않는다.
  - 변경·취소 정책이 미확정이므로 현재 수정·삭제는 제공하지 않는다. 연결된 작업지시 건수는 조회만 하며 상태·달성률로 해석하지 않는다.
  - 초과 배분 허용 여부, 계획 변경·취소 조건, 생산 달성수량의 기준은 **설계 결정 필요**.
- **출력 데이터:** 생산계획, 연결된 작업지시, 배분·생산 현황
- **예외 상황:** 잘못된 수량·일정, 배분수량 미만으로 계획 축소, 진행 중 계획 취소
- **연관 도메인:** 품목, 작업지시, 생산실적

### FR-06. 작업지시 관리

- **목적:** 생산계획을 실행 가능한 작업 단위로 구체화한다.
- **주요 사용자:** 생산관리 담당자, 생산 작업자
- **입력 데이터:** 생산계획, 생산 품목, 지시수량, 작업 일정, BOM 버전, Routing
- **처리 규칙:**
  - 생산계획과 연결하고 적용 BOM·Routing을 식별한다.
  - 6차 BR-11: 계획·BOM 버전·Routing 개정의 정확한 PK와 제품 일치를 검증하고 READY를 등록한다. 계획 초과 배분은 안내만 하며 임의 차단하지 않는다.
  - 신규 수량은 1~999999999999 정수다. 현재 미사용 공정이 포함된 Routing은 신규 지시에서 거부하되 기존 지시 진행·과거 스냅샷은 유지한다.
  - first_used_at NULL만 기록하고 지시 INSERT와 원자 저장한다. 시작·시작 전 취소를 제공하며 완료 처리는 생산실적 구현과 연계한다.
  - 상태에 따라 허용되는 작업을 제어한다.
  - 취소·변경 시 원자재 예약·투입, 생산실적, LOT에 미치는 영향을 함께 검토한다.
  - 허용 전이는 `READY → IN_PROGRESS → COMPLETED` 및 `READY → CANCELLED`다. 다른 전이를 추가하지 않는다.
  - `COMPLETED`는 생산실적이 존재하고 0보다 큰 누적 생산수량이 지시수량과 같을 때만 허용한다. 미달·0수량·실적 없음은 완료를 거부하고 초과 생산도 금지한다. 생산 양품·검사 합격수량으로 완료를 판단하지 않는다.
  - 생산 완료와 품질검사 결과는 독립적으로 관리하며 검사 완료·합격을 완료 조건으로 요구하지 않는다.
  - 투입·생산실적 이력이 있는 작업지시의 일반 취소는 금지한다. 완료 후 사후 정정은 MVP에서 제외한다.
- **출력 데이터:** 작업지시 상세, 상태, 실적 현황, 원자재 사용 내역
- **예외 상황:** 허용되지 않은 상태 전이, 부적합한 BOM·Routing, 관련 이력이 있는 작업지시 취소
- **연관 도메인:** 생산계획, BOM, Routing, LOT, 생산실적, 품질검사

### FR-07. 원자재 LOT 및 투입 관리

- **목적:** 원자재를 LOT별로 식별하고 생산에 사용한 수량과 이력을 관리한다.
- **주요 사용자:** 생산관리 담당자, 생산 작업자
- **입력 데이터:** LOT 등록은 LOT 번호·품목·최초 등록수량, 실제 소비는 작업지시·확정 BOM 구성·원자재 LOT·투입수량이다. 등록일시·소비시각·작성자는 서버가 기록한다. 소비 요청 UUID는 신규 화면에서 생성해 재전송에 유지한다.
- **처리 규칙:**
  - 2026-10-27 개발자 승인: LOT 번호는 원자재 LOT 전체에서 전역 유일하다. 품목이 달라도 같은 번호를 쓸 수 없으며 기존 DB UNIQUE와 사전 조회로 보호한다. 자동 채번·등록 후 번호 변경은 제공하지 않는다. 완제품 LOT 번호 정책에는 영향을 주지 않는다.
  - 신규 LOT에는 현재 활성 RAW 품목만 사용한다. 품목 행 잠금 후 최신 상태·단위를 재검증한다. 작성자는 기존 MES_ACTOR_ID를 사용한다.
  - 최초 등록수량은 양수이며 EA 정수, M·G 소수 6자리 및 DECIMAL(18,6) 범위를 따른다. 0·음수·초과 정밀도·범위 초과를 거절하고 자동 반올림·절삭·단위 환산을 하지 않는다. 신규 가용수량은 최초 등록수량과 같은 값으로 같은 트랜잭션에서 저장한다. 이후 정상 소비로 가용수량이 0이 되는 것은 허용한다.
  - registered_at은 서버가 등록 순간 UTC_TIMESTAMP(6)으로 기록하며 사용자 입력·소급 등록·수정을 제공하지 않는다. created_at은 별도 시스템 기록시각으로 유지한다. 화면은 기존 공통 UTC→Asia/Seoul 변환으로 KST를 표시한다.
  - 목록·등록·상세를 제공한다. 목록에서 LOT 번호·원자재 코드·명칭을 검색하고 구분·보존 단위·등록수량·가용수량·등록 업무시각을 표시한다. 상세에서 실제 소비·반환·순소비 합계를 독립 집계하며 가용수량 불일치는 보정 없이 안내한다.
  - LOT 등록·조회는 BR-12, 8차 실제 소비는 BR-13을 따른다. 최초 등록수량·가용수량 직접 수정, LOT 삭제, 반환 생성, 재고 조정·입고 추가·폐기·창고 이동은 제공하지 않는다.
  - 투입 원자재 LOT과 작업지시, 사용수량의 연결 이력을 남긴다.
  - 같은 LOT에 대한 동시 투입으로 허용 수량을 초과하지 않도록 한다.
  - IN_PROGRESS에서 BOM 구성 원자재를 투입하며, 투입 등록은 실제 소비 확정이다. 가용수량 차감과 사용 이력 저장은 동일 트랜잭션에서 처리한다.
  - 실제 소비량과 BOM 예상 소요량 및 차이를 조회하며 예상량으로 실제값을 자동 보정하지 않는다. 차이 자체는 MVP에서 자동 차단하지 않는다. BOM 외 자재와 LOT 가용수량 초과 투입은 차단한다.
  - IN_PROGRESS에서만 일반 투입 정정·반환을 허용한다. 소비 원본을 물리 삭제하지 않고 원래 투입에 연결된 별도 정정·반환 이력을 보존한다. 반환은 반환 가능한 기존 순소비수량을 초과할 수 없고 소비하지 않은 자재를 반환 처리하지 않는다.
  - 반환 이력 저장과 LOT 가용수량 복원은 동일 트랜잭션에서 처리한다. COMPLETED의 일반 투입 정정·반환은 금지한다.
  - 원자재 투입·생산실적 등록에 요청 고유 ID를 사용하며 DB 유일성 제약으로 재전송의 중복 반영을 방지한다. 원자재 소비는 작성자 SHA-256 범위·UUID·정규화 payload v1·최초 성공 JSON을 사용하는 BR-13의 승인 계약으로 구현한다. 같은 키·같은 내용은 최초 소비 상세로 이동하며 현재 상태/재고 때문에 재차 소비하지 않는다. 다른 내용은 거부한다. 생산실적 계약은 별도 결정한다.
  - Receipt → WorkOrder → RawLot 잠금, 조건부 차감, 소비 원장, 요청 성공 기록은 한 트랜잭션이다. Receipt UNIQUE 충돌 후 기존 성공 확인은 실패 트랜잭션 롤백 뒤 별도 Spring 프록시의 새 읽기 트랜잭션으로 수행한다. 실패한 요청의 Receipt·재고·소비는 모두 롤백한다.
  - 투입 목록·검색·등록·소비 상세와 작업지시 상세의 이력 링크를 제공한다. consumed_at은 UTC_TIMESTAMP(6)으로 기록하고 화면만 KST로 변환한다. 최초 성공 재고 전후값과 현재 가용수량을 별도로 표시한다. BOM 예상량·순소비·차이는 정확히 계산하며 유한 소수가 아니면 나눗셈 식으로 표시한다.
  - 예약 도입 여부는 **설계 결정 필요**. 가용수량·순소비수량의 저장·집계 구조는 후속 ERD에서 결정한다.
- **출력 데이터:** LOT별 수량 현황, 투입·반환 이력, 연결 작업지시
- **예외 상황:** LOT 중복, 수량 부족, 잘못된 품목 투입, 사용 제한 LOT 투입
- **연관 도메인:** 품목, BOM, 작업지시, 생산실적, LOT 추적

### FR-08. 생산실적 관리

- **목적:** 작업지시의 실제 생산 결과를 기록한다.
- **주요 사용자:** 생산 작업자, 생산관리 담당자
- **입력 데이터:** 작업지시, 생산일시, 생산수량, 양품수량, 불량수량, 작업자, 생산 LOT
- **처리 규칙:**
  - **생산수량 = 양품수량 + 불량수량**을 만족해야 한다.
  - 실적과 작업지시, 생산 LOT의 관계를 유지한다.
  - 실적 수정 이력을 확인할 수 있어야 한다.
  - 일반 실적 등록·정정은 IN_PROGRESS에서만 허용한다. COMPLETED 이후 및 품질검사 이후 일반 정정은 금지한다.
  - 정정 이력을 보존하고 누적 생산수량과 LOT 관련 집계의 정합성을 유지한다. 실적 정정으로 원자재 소비량을 자동 변경하지 않는다.
  - 실적 등록·정정 후 누적 생산수량이 지시수량을 초과하면 거부한다. 등록 요청 고유 ID와 DB 유일성 제약으로 동일 요청 재전송의 중복 반영을 방지한다.
  - 실적 취소의 상세 절차는 **설계 결정 필요**. 수량의 저장·집계 방식은 후속 ERD에서 결정한다.
  - 생산 양품과 품질검사 합격은 별도 수량으로 관리하며, 검사 불합격을 생산 불량에 무조건 합산하지 않는다.
- **출력 데이터:** 실적 상세·집계, 작업지시별 누적수량, 수정 이력
- **예외 상황:** 수량 불일치, 음수 수량, 불량수량 초과, 중복 등록, 허용되지 않은 상태의 등록
- **연관 도메인:** 작업지시, 원자재 LOT, 완제품 LOT, 불량, 품질검사

### FR-09. 완제품 LOT 관리

- **목적:** 생산된 제품을 추적 가능한 단위로 식별한다.
- **주요 사용자:** 생산관리 담당자, 품질 담당자
- **입력 데이터:** LOT 번호, 생산 품목, 작업지시·생산실적 연결, 생성일시. 생산·검사 관련 수량은 연결된 원천 데이터와 구분한다.
- **처리 규칙:**
  - LOT 번호 중복을 방지한다.
  - 완제품 LOT에서 생산 근거와 원자재 사용 이력을 찾을 수 있어야 한다.
  - 최초 생산실적 등록 시 생성하며, 하나의 작업지시에는 최대 하나의 완제품 LOT만 연결한다.
  - 누적 생산수량 = 누적 생산 양품수량 + 누적 생산 불량수량을 유지한다.
  - 재검사·재작업·중복 검사 대상이 없는 MVP에서 누적 생산 양품수량 = 미검사수량 + 검사 합격수량 + 검사 불합격수량을 유지한다.
  - 원천 데이터 저장과 집계 계산의 구분은 후속 ERD에서 결정한다. 취소·삭제 정책은 **설계 결정 필요**.
- **출력 데이터:** 완제품 LOT 상세, 생산 근거, 누적 생산·생산 양품·생산 불량·검사 합격·검사 불합격·미검사 수량, 검사 상태·이력
- **예외 상황:** 중복 LOT, 생산실적과 수량 불일치, 연결 실적 취소, 검사 완료 후 수량 변경
- **연관 도메인:** 작업지시, 생산실적, 품질검사, LOT 추적

### FR-10. 불량 관리

- **목적:** 불량수량과 발생 사유를 생산 이력에 연결하여 기록한다.
- **주요 사용자:** 생산 작업자, 품질 담당자
- **입력 데이터:** 생산실적 또는 검사 대상, 불량유형, 불량수량, 발생일시, 설명
- **처리 규칙:**
  - 불량 기록의 발생 근거를 식별할 수 있어야 한다.
  - 생산실적 불량과 검사에서 발견한 불량의 중복 집계를 방지할 규칙이 필요하다.
  - 생산 불량과 검사 불합격을 별도로 기록한다. 검사 불합격으로 생산실적 불량을 덮어쓰거나 자동 합산하지 않는다. 중복되지 않는 수량임이 보장되면 전체 부적합 통계로 합산할 수 있다.
  - 유형별 수량 합산 기준, 한 제품의 복수 불량 기록, 폐기 처리는 **설계 결정 필요**. 재검사·재작업은 MVP에서 제외한다.
- **출력 데이터:** 불량 내역, 유형별·작업지시별 집계
- **예외 상황:** 대상 수량 초과, 중복 기록, 실적 불량수량과 상세 합계 불일치
- **연관 도메인:** 생산실적, 품질검사, LOT

### FR-11. 품질검사 관리

- **목적:** 생산 결과에 대한 품질 판정과 검사 이력을 관리한다.
- **주요 사용자:** 품질 담당자
- **입력 데이터:** 검사 대상, 회차별 검사 대상수량·합격수량·불합격수량, 검사일시, 검사자, 검사 결과, 판정 사유
- **처리 규칙:**
  - `PASS`, `FAIL` 등의 판정 상태와 수량 정보를 구분한다. 부분 합격 LOT의 요약 상태명·판정 매핑은 후속 설계에서 결정한다.
  - 검사 대상과 결과의 연결 이력을 유지한다.
  - 미검사 상태를 합격으로 취급하지 않는다.
  - 최종 품질검사는 COMPLETED 작업지시에서만 등록한다. READY·IN_PROGRESS·CANCELLED에서는 거부한다. Routing의 기능검사와 구분한다.
  - 검사 전체 대상은 생산 완료 시 확정된 누적 생산 양품수량이며 생산 불량은 제외한다.
  - 회차별 대상수량 = 합격수량 + 불합격수량을 검증한다. 여러 차례 등록할 수 있지만 누적 검사수량은 확정된 생산 양품수량을 초과할 수 없으며 동일 대상 수량의 중복 검사를 서버에서 방지한다.
  - 합격·불합격·미검사 수량을 각각 조회한다. 불합격이어도 작업지시 상태를 자동 복귀시키지 않는다. 재검사·재작업은 MVP에서 제외한다.
  - 누적 검사수량 상한 검증만으로 동일 대상의 중복 검사 방지가 보장된다고 간주하지 않는다. 개별 검사 대상 식별의 필요성·식별 단위·중복 방지 DB 구조는 ERD 검토 항목으로 남긴다. 불합격 제품의 후속 처리와 LOT 요약 품질 상태 등은 **설계 결정 필요**.
  - 출고 기능을 포함한다면 검사 전·불합격 LOT의 출고 정책을 별도로 결정한다.
- **출력 데이터:** 검사 결과·이력, 대상 LOT의 품질 상태
- **예외 상황:** 대상 없는 검사, 판정 누락, 중복 검사, 취소된 생산 대상 검사
- **연관 도메인:** 생산실적, 완제품 LOT, 불량

### FR-12. LOT Traceability

- **목적:** 완제품의 생산 근거와 원자재 출처를 추적한다.
- **주요 사용자:** 생산관리 담당자, 품질 담당자, 조회 담당자
- **입력 데이터:** 완제품 LOT 번호, 정방향 추적 지원 시 원자재 LOT 번호
- **처리 규칙:**
  - 완제품 LOT에서 작업지시·생산실적·사용 원자재 LOT을 조회한다.
  - 현재 BOM으로 과거 투입 원자재를 추정하지 않고 실제 사용 이력을 조회한다.
  - 작업지시당 완제품 LOT은 최대 하나다. 작업지시 단위 원자재 투입량을 개별 생산실적에 임의 배분하지 않는다.
  - 원래 소비 이력과 연결된 정정·반환 이력 및 반영 후 순소비수량을 추적할 수 있어야 한다.
  - 작업지시 단위 연결만 존재하면 조회 결과에서도 그 추적 범위를 명시한다.
- **출력 데이터:** LOT 간 연결 관계, 작업지시, 생산실적, 원자재 사용 이력, 관련 검사 정보
- **예외 상황:** LOT 미존재, 투입 이력 누락, 취소·정정 기록과의 연결, 수량 귀속 불명확
- **연관 도메인:** LOT, 작업지시, 생산실적, BOM, 품질검사

| DI-06 | 변경·취소 시 관련 상태, 수량, 이력이 서로 모순되지 않아야 한다. |

| DI-10 | 생산실적 정정 전후의 내용과 관련 LOT에 미친 영향을 확인할 수 있어야 한다. |

구체적인 트랜잭션 범위, 잠금 방식, DB 제약조건은 비즈니스 규칙과 DB 설계 단계에서 결정한다.

## 7. 기술 및 구조 제약

| 영역 | 기준 |
|---|---|
| Backend | Java 17, Spring Boot, Spring MVC, MyBatis, Gradle |
| Database | MySQL |
| Frontend | Thymeleaf, JavaScript |
| Test | JUnit 5, Spring Boot Test |
| Infra | Docker, Linux, Nginx |

도메인 패키지는 `com.taehyung.mes` 아래 `item`, `bom`, `process`, `routing`, `production`, `workorder`, `lot`, `quality`, `trace`, `common`으로 구성한다.

- Controller는 요청·응답 처리를 담당한다.
- Service는 비즈니스 규칙과 업무 흐름을 담당한다.
- Mapper는 데이터 접근을 담당한다.
- 새로운 프레임워크나 라이브러리는 임의로 도입하지 않는다.
- 기존 코드가 있다면 해당 구조와 명명 규칙을 우선 확인한다.

## 8. 비기능 요구사항

### 8.1 오류 처리 및 운영 기록

- 업무 규칙 위반을 예외 무시나 임의의 기본값으로 우회하지 않는다.
- 사용자가 조치할 수 있도록 오류 원인을 구분하여 전달한다.
- 주요 변경의 작업자와 시점을 확인할 수 있도록 한다.
- 장애 원인을 조사할 수 있는 로그를 남긴다.
- 로그 범위와 보존 기간은 **설계 결정 필요**.

### 8.2 보안 및 데모 운영

- 로그인, 조회·변경 권한, 공개 데모의 데이터 변경 허용 범위는 **설계 결정 필요**.
- 인증정보와 운영 비밀값을 소스 코드에 포함하지 않는다.
- 실제 접근 가능한 데모 사이트 운영을 목표로 한다.

### 8.3 배포

- Docker 기반 애플리케이션을 Linux 환경에 배포하고 Nginx를 구성한다.
- HTTPS, Health Check, 이미지 버전 관리, Rollback, 로그 확인 절차는 구축 목표로 둔다.
- 백업·복구 방식과 운영 데이터 보존 정책은 **설계 결정 필요**.

### 8.4 성능

예상 사용자 수, 동시 요청 수, 데이터 규모 및 응답시간 목표가 제공되지 않아 현재 수치 기준은 정할 수 없다. 이후 조회 범위와 운영 규모를 기준으로 확정한다.

## 10. 우선 결정할 업무 정책

최초 실적 시 LOT 생성, 투입 시 소비 확정, 수량 구분, 완료 후 검사, 일반 정정 가능 상태는 `business-rules.md`를 따른다. 누적 생산수량과 지시수량 일치에 의한 완료, 초과·0수량·실적 없는 완료 금지, BOM 편차 자체의 자동 차단 금지, IN_PROGRESS 원자재 정정·반환, 투입·실적 등록의 요청 고유 ID 정책도 확정 기준이다. 남은 항목은 다음과 같다.

| 우선순위 | 결정 항목 | 결정이 필요한 이유 |
|---|---|---|
| 1 | 개별 검사 대상 식별의 필요성·식별 단위·중복 방지 구조 | 누적 상한 검증과 개별 대상 중복 검증을 구분하여 ERD에서 검토 |
| 2 | 원자재 예약 여부 및 투입 정정·반환 이력 저장 구조 | 예약은 업무 결정, 승인된 반환 규칙의 연결·집계는 기술 설계 |
| 3 | 실적 취소의 상세 절차 | 확정된 상태 전이·일반 정정 제한 내에서 미확정 절차 구체화 |
| 4 | LOT 관련 원천 데이터 저장·집계 계산 방식 | 작업지시 단위 추적과 누적수량 정합성 유지 |
| 5 | 부분 합격 LOT의 요약 품질 상태와 가용수량 모델 | 구분된 생산·검사 수량의 상태 표현 |
| 6 | 생산계획 초과 배분 허용 여부 | 작업지시 초과 생산 금지와 구분되는 계획 배분 정책 결정 |
| 7 | BOM·Routing 확정 시점과 변경 정책 | 과거 생산 기준 보존 |
| 8 | 정정 이력 저장 구조와 완료 LOT 삭제 정책 | 일반 정정 가능 상태는 확정, 이력 구조는 기술 설계, LOT 삭제는 업무 결정 |
| 9 | 검사 불합격 후속 처리와 LOT 요약 상태 | 재검사·재작업 제외 범위에서 후속 정책 결정 |
| 10 | 정방향 추적, 권한, 재고·출하의 MVP 범위 | 개발 범위 확정 |

요청 고유 ID의 사용과 DB 유일성 보장은 확정했으며 저장 위치·유일성 범위·중복 요청 응답 방식은 후속 기술 설계에서 결정한다.

## 11. AI 활용 및 검증 원칙

- AI는 코드 탐색, 구현 초안, 리뷰, 영향 분석, 문서 작성을 보조한다.
- 업무 정책, DB 구조, 트랜잭션, 상태 전이 및 운영 정책은 개발자가 최종 결정한다.
- 미확정 정책을 구현 편의에 맞춰 임의로 정하지 않는다.
- AI 오류는 제안 내용, 문제, 위험, 검증 근거, 수정 내용을 기록한다.
- 구현 결과는 Diff와 기존 패턴을 검토하고, 승인된 검증 범위에서 테스트·SQL·DB·로그를 확인한다.
- 프로젝트 규칙에 따라 빌드·테스트·린트는 명시적 요청이 있을 때만 실행한다.

## 12. 후속 작업

`business-rules.md`의 확정 정책을 기준으로 남은 업무 결정을 정리하고, 검사 대상 식별·중복 방지와 원천 데이터·집계의 구분을 포함한 ERD 설계를 진행한다. 이 문서의 기존 FR-01~FR-12, DI-01~DI-10, AC-01~AC-12를 유지하면서 상세 정책은 Business Rules에서 관리한다.
